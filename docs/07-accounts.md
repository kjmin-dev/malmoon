# 계정과 로그인

Malmoon은 관리형 인증 서비스나 인증 프레임워크 없이, 자체 데이터베이스(PostgreSQL)에 계정을 둔다. 이메일 코드와 Google, Apple, 카카오, LINE으로 로그인하고, 한 계정에 여러 로그인 방법을 연결한다. 구현은 `crates/malmoon-auth`에 있고 게이트웨이가 그 경로를 그대로 싣는다.

## 계정 모델

사람은 `users`, 로그인 방법은 `identities`다. 사용자 하나가 로그인 방법을 여럿 가진다.

| 테이블 | 내용 |
| --- | --- |
| `users` | 사람. 표시 이름만 가진다 |
| `identities` | 로그인 방법 하나. `(provider, subject)`가 고유하다 |
| `sessions` | 로그인한 기기 하나. 토큰의 SHA-256만 저장한다 |
| `oauth_flows` | 공급자에게 다녀오는 동안의 상태. 한 번 쓰면 지운다 |
| `login_codes` | 앱이 세션으로 바꾸는 일회용 코드. 60초 동안 유효하다 |
| `email_challenges` | 이메일로 보낸 6자리 코드의 해시와 시도 횟수 |

설계에서 지킨 것은 세 가지다.

- **사용자를 이메일로 식별하지 않는다.** `identities.subject`는 공급자가 주는 고정 식별자(OpenID Connect의 `sub`)다. 공급자가 알려 주는 이메일은 바뀔 수 있고, Apple은 앱마다 다른 가상 주소를 준다.
- **이메일 로그인도 로그인 방법의 하나다.** 공급자는 `email`, 식별자는 주소다. 이메일과 소셜 로그인이 같은 규칙으로 연결되고 해제된다.
- **이메일의 검증 여부를 공급자별로 따로 기록한다.** 공급자가 주소의 소유를 보증할 때만 `email_verified`가 참이다.

## 로그인 방법

### 이메일 코드

비밀번호가 없다. 주소로 6자리 코드를 보내고, 코드를 입력하면 가입과 로그인이 한 번에 끝난다. 비밀번호 저장, 재설정, 유출 대응이 필요 없고, 코드를 입력한 것이 곧 주소 검증이다.

| 제한 | 값 |
| --- | --- |
| 코드 유효 시간 | 10분 |
| 코드 하나의 입력 시도 | 5회 |
| 같은 주소로 다시 보내기 | 60초 뒤 |
| 같은 주소로 보내는 횟수 | 1시간에 5회 |

계정이 있든 없든 응답이 같아서, 이 요청으로 가입 여부를 알아낼 수 없다.

### 소셜 로그인

게이트웨이가 OAuth 클라이언트다. 공급자의 클라이언트 비밀과 토큰은 서버에만 있고, 앱은 공급자와 직접 통신하지 않는다. 그래서 세 플랫폼의 흐름이 같다.

1. 앱이 무작위 검증 값(PKCE)을 만들고, 그 해시와 돌아올 주소를 담아 `POST /v1/auth/oauth/{provider}/start`를 부른다.
2. 받은 주소를 브라우저로 연다. 웹은 페이지 이동, 모바일은 인앱 브라우저다.
3. 공급자가 게이트웨이의 콜백으로 돌려보낸다. 게이트웨이가 코드를 ID 토큰으로 바꾸고, 발급자, 대상, 만료, nonce를 확인한다.
4. 게이트웨이가 일회용 로그인 코드를 붙여 앱의 주소로 돌려보낸다.
5. 앱이 로그인 코드와 검증 값을 `POST /v1/auth/token`에 보내 세션을 받는다.

로그인 코드는 주소에 실려 오지만, 검증 값을 아는 앱만 세션으로 바꿀 수 있다. 주소가 기록이나 다른 앱으로 새어도 쓸 수 없다.

돌아올 주소는 클라이언트 종류별로 제한한다.

| 클라이언트 | 허용하는 주소 |
| --- | --- |
| 웹 | 등록한 웹 출처의 경로 |
| 데스크톱 | `http://127.0.0.1:{포트}/callback` (RFC 8252) |
| 모바일 | 등록한 앱 주소와 정확히 같은 것 (`malmoon://auth/callback`) |

공급자별 차이는 다음과 같다.

| 공급자 | 이메일 검증 여부 | 비고 |
| --- | --- | --- |
| Google | ID 토큰의 `email_verified` | |
| Apple | 항상 검증된 것으로 본다 | 클라이언트 비밀이 ES256 JWT다. 콜백이 POST 폼으로 온다. 이름은 첫 로그인에만 온다 |
| 카카오 | ID 토큰에 없어서 userinfo로 확인한다 | 콘솔에서 OpenID Connect를 켜야 한다. 이메일 동의 항목은 비즈 앱 전환과 심사가 필요하다 |
| LINE | 검증되지 않은 것으로 본다 | 문서가 검증 여부를 밝히지 않는다. 이메일 권한을 콘솔에서 신청해야 한다 |

ID 토큰의 서명은 확인하지 않는다. 토큰을 브라우저를 거치지 않고 공급자의 토큰 엔드포인트에서 TLS로 직접 받기 때문이고, OpenID Connect Core 3.1.3.7이 이 경우를 허용한다. 앱이 ID 토큰을 직접 보내는 방식(iOS의 네이티브 Apple 로그인)을 추가하려면 서명 검증이 필요하다.

### 데스크톱

데스크톱 앱에는 로그인 화면이 없다. 로그인 버튼을 누르면 시스템 브라우저로 웹 앱을 열고, 사용자는 웹에서 아무 방법으로나 로그인한 뒤 "데스크톱 앱에 로그인"을 승인한다. 웹이 `POST /v1/auth/handoff`로 로그인 코드를 받아 데스크톱 앱이 듣고 있는 루프백 주소로 브라우저를 보내고, 데스크톱 앱이 그 코드를 자기 세션으로 바꾼다.

이 컴퓨터의 어떤 프로그램이든 그 웹 페이지를 열 수 있으므로, 웹에 이미 로그인되어 있어도 승인 없이는 넘기지 않는다.

## 계정 연결

새 로그인 방법이 들어왔을 때의 규칙이다.

| 상황 | 결과 |
| --- | --- |
| 이미 아는 로그인 방법이다 | 그 계정으로 로그인한다 |
| 로그인한 사용자가 연결을 요청했다 | 그 계정에 추가한다. 다른 계정의 것이면 거절한다 (`identity_in_use`) |
| 처음 보는 방법이고, 공급자가 검증한 이메일을 한 계정이 검증된 것으로 갖고 있다 | 그 계정에 자동으로 연결한다 |
| 처음 보는 방법이고, 이메일이 다른 계정의 것인데 공급자가 검증하지 않았다 | 거절한다 (`email_in_use`). 기존 방법으로 로그인한 뒤 직접 연결하게 한다 |
| 그 밖 | 새 계정을 만든다 |

자동 연결은 양쪽이 같은 메일함의 소유를 증명했을 때만 한다. 검증되지 않은 주소로 연결하면, 남의 주소를 적어 넣은 공급자 계정으로 그 사람의 계정에 들어갈 수 있다. 반대 순서도 막는다. 검증되지 않은 주소로 먼저 만든 계정은 나중에 진짜 소유자가 로그인해도 합쳐지지 않는다.

마지막 로그인 방법은 해제할 수 없다 (`last_identity`).

## 세션

세션 토큰은 무작위 256비트 값이고, 서버는 해시만 저장한다. 요청마다 데이터베이스에서 확인하므로 로그아웃하면 바로 무효가 된다. 30일 동안 유효하고, 쓰는 동안 연장된다.

| 클라이언트 | 보관 위치 | 전송 |
| --- | --- | --- |
| 웹 | `HttpOnly`, `SameSite=Lax` 쿠키. 스크립트가 읽을 수 없다 | 브라우저가 붙인다 |
| 데스크톱 | 운영체제 키체인 (디버그 빌드는 사용자만 읽는 파일) | `Authorization: Bearer` |
| 모바일 | 키체인과 키스토어 (`expo-secure-store`) | `Authorization: Bearer` |

쿠키로 인증한 요청은 값을 바꾸는 요청과 WebSocket 연결에서 `Origin`이 등록한 웹 출처인지 확인한다. 웹 앱과 게이트웨이는 브라우저가 같은 사이트로 보는 주소에 있어야 한다. 개발 환경에서는 둘 다 `localhost`다.

실시간 세션(`/v1/session`)은 로그인한 사용자만 연다. 없으면 WebSocket으로 바뀌기 전에 401로 거절한다.

## API

| 경로 | 내용 |
| --- | --- |
| `GET /v1/auth/providers` | 이 서버가 받는 로그인 방법 |
| `POST /v1/auth/email/start` | 코드를 보낸다 |
| `POST /v1/auth/email/verify` | 코드를 확인하고 세션을 만든다 |
| `POST /v1/auth/oauth/{provider}/start` | 소셜 로그인을 시작하고 열 주소를 준다 |
| `GET, POST /v1/auth/oauth/{provider}/callback` | 공급자가 돌아오는 곳 |
| `POST /v1/auth/token` | 로그인 코드를 세션으로 바꾼다 |
| `POST /v1/auth/handoff` | 웹 세션으로 데스크톱 앱을 로그인시킨다 |
| `POST /v1/auth/logout` | 세션을 끝낸다 |
| `GET /v1/me` | 계정과 로그인 방법 |
| `DELETE /v1/me/identities/{id}` | 로그인 방법을 해제한다 |

오류는 `{"error": {"code", "message"}}`로 답하고, 클라이언트는 `code`로 분기한다.

## 설정

| 환경 변수 | 내용 |
| --- | --- |
| `DATABASE_URL` | PostgreSQL 주소 |
| `MALMOON_PUBLIC_URL` | 브라우저가 게이트웨이에 닿는 주소. 공급자에 등록하는 콜백은 `{이 주소}/v1/auth/oauth/{provider}/callback`이다 |
| `MALMOON_WEB_ORIGINS` | 웹 앱의 출처. 쉼표로 구분한다 |
| `MALMOON_APP_REDIRECTS` | 모바일 앱이 돌아올 주소 |
| `MALMOON_GOOGLE_CLIENT_ID`, `MALMOON_GOOGLE_CLIENT_SECRET` | Google |
| `MALMOON_KAKAO_CLIENT_ID`, `MALMOON_KAKAO_CLIENT_SECRET` | 카카오. ID는 REST API 키이고, 비밀은 콘솔에서 끈 경우 생략한다 |
| `MALMOON_LINE_CLIENT_ID`, `MALMOON_LINE_CLIENT_SECRET` | LINE. ID는 채널 ID다 |
| `MALMOON_APPLE_CLIENT_ID`, `MALMOON_APPLE_TEAM_ID`, `MALMOON_APPLE_KEY_ID`, `MALMOON_APPLE_PRIVATE_KEY` | Apple. ID는 서비스 ID다 |

클라이언트 ID를 넣은 공급자만 켜진다. 아무것도 넣지 않으면 이메일 로그인만 된다.

## 확인한 것과 남은 일

통합 테스트는 실제 PostgreSQL과 공급자 역할을 하는 대역 서버로 돈다. 실제 공급자 네 곳에는 연결해 보지 않았다. 앱 등록과 키가 있어야 한다.

| 항목 | 상태 |
| --- | --- |
| 메일 발송 | 없다. 코드를 서버 로그에 쓴다. 배포 전에 발송 서비스를 붙여야 한다 |
| 실제 공급자 연동 | 확인하지 않았다 |
| IP 단위 요청 제한 | 없다. 주소 단위 제한만 있다 |
| 계정 삭제 | 없다. App Store는 앱 안에서 계정을 삭제할 수 있어야 한다 |
| iOS의 네이티브 Apple 로그인 | 없다. 지금은 인앱 브라우저로 한다 |
| 기기 목록과 원격 로그아웃 | 없다 |
| 모바일 앱 | 타입 검사와 번들링만 확인했다. 기기에서 실행하지 않았다 |
